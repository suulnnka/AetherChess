# 国际象棋引擎评估函数升级:三方参照与实施方案

> **迁移说明(2026-09)**:本引擎已从 webos 仓库抽离为独立仓库 **AetherChess**。路径对照:
> `src/rules.js` / `src/ai.js` / `src/eval.js` / `src/worker.js`(原 `js/apps/chess3d/` 下同名文件,worker 原名 `ai-worker.js`);
> `test/engine-test.mjs`(原 `tools/chess-engine-test.mjs`);`bench/*`(原 `tools/chess-bench*.mjs` / `tools/uci-match.mjs`);
> `tuner/`(原 `tools/chess-eval-tuner/`)。3D UI(`index.js`)与产物级/浏览器级测试(worker 冒烟、probe)留在 webos 侧。
> 文中如再出现 `js/apps/...`、`index.js`、`npm run build`(webos 的构建闸门)等字样,均为当时的历史记述。

> 起因:`docs/chess-ai-plan.md` §3.4/§9.5 的结论 —— 本引擎 ≈2030 Elo,瓶颈已从"看得不够深"
> 转到"看得再深也评不准";对照物 Wasabi 用**不到我们 1/4 的参数**、在同棋力下少用 **16.7 倍**节点。
> 本文回答:照 Wasabi 改评估函数可行吗?旧版 Stockfish 的经典估值还值不值得参考?
>
> **一句话结论:结构可以大胆借,数值一个都不能抄(两者都是 GPL-3.0)。真正的活是给自己写一个调参器。**

## 一、三方估值构成对照

参数个数均为**逐个点出来的**(Wasabi 读 `assembly/board.ts`+`pieces.ts`;SF 读 `sf_11` 标签下
`evaluate.cpp`/`psqt.cpp`/`pawns.cpp`/`material.cpp`;本引擎读 `src/ai.js`)。

| 估值项 | 本引擎 | Wasabi | SF 11 经典估值 |
|---|---|---|---|
| 子力 | 10 | 10 | ✅ + **IMBALANCE**(42) |
| PSQT / PST | **768**(6 表 × 64 格 × 2 相位) | **无** | **416**(半列镜像,**见 §三.8**) |
| 机动性 | **无** | **132**(4 子 × MG/EG) | **132**(`MobilityBonus`,66 个 Score 各含 MG/EG) |
| 兵结构 | 4(叠兵/孤立兵) | 3(叠兵/通路/掩护) | **69**(孤立/叠兵/落后/连通/候选通路 + 王前盾 + 攻击风暴) |
| 通路兵 | 无 | ✅(按距升变距离) | ✅ + rank 表 + 王距缩放 |
| 王安全 | 1(王盾) | 2(王盾 + 王区威胁) | **最多**(攻击者权重 / 安全将军 / kingRing / 侧翼 / 护王) |
| 威胁类 | 无 | 无 | ✅ **THREAT**(`ThreatByMinor`/`ThreatByRook`/挂子/过载) |
| 空间 | 无 | 无 | ✅ **SPACE** |
| 主动权 / 走子奖励 | 无 | 无 | ✅ **INITIATIVE**(tempo ≈ 28) |
| 残局缩放 / 和棋判定 | 1(子力不足) | 3(无兵和棋阈值) | ✅ `endgame.cpp` 一整套(KXK/KBNK/异色象…) |
| 易位权 | 无 | ✅(已易位 / 丢权惩罚) | 隐含于 PST + 王安全 |
| **合计(点得出的参数)** | **≈ 796** | **≈ 165** | **≈ 735**(未含 `endgame.cpp` 缩放因子) |
| **参数怎么来的** | 手写,零调参 | 725,000 局面回归调参 | **SPSA 自动调参**(多年) |

**最该先看到的一件事:我们的参数量(~796)和 SF 11 经典估值(~735)是同一量级** ——
所以"参考 SF 旧版"**不是让我们把估值做大**,而是**把结构从"一大块 PST"换成"许多小的、有意义的、
可独立调参的项"**。同样的参数量,分给 9 类项,还是全塞进一张表,棋力完全不同。

## 二、从 Wasabi 借什么(4 项,都已在其源码里验证过)

1. **机动性,而且是"安全机动性"**
   `board.ts` 里先算 `whiteSafeTargets = (空位 | 黑子) & ~黑兵攻击格`,再按落点数查表。
   即"对方兵能控制的格子不算我的机动性" —— 比常见的裸机动性讲究,且几乎不要额外成本。
   **机动性表的值要按子分别给 MG/EG 两套**(它的 `KNIGHT_MOB_BONUS` / `EG_KNIGHT_MOB_BONUS`)。
2. **通路兵按"距升变距离"加成,且 MG/EG 分开**
   `PASSED_PAWN_BONUS * reversedDistance`,外加一个指数项让"第 7 横线的通路兵"异常值钱。
   SF 11 的 `PassedRank[RANK_NB] = { S(0,0), S(10,28), S(17,33), S(15,41), S(62,72), S(168,177), S(276,260) }`
   把这条规律讲得更清楚:中局值从第 3 横线的 **17** 一路涨到第 7 横线的 **276**(**16 倍**)。
   **"通路兵"不是一个数,是一条曲线** —— 用单个常数去表达它,等于把这个最锋利的残局武器磨平。
   本引擎现在完全没有通路兵项 —— 这是残局最贵的缺口。
3. **王区威胁用"攻击者计数 → 非线性惩罚表"**
   `KING_DANGER_ZONE_PATTERNS[王的位置]` 给出危险区,`KING_DANGER_PIECE_PENALTY[威胁数]`
   是一张 0→1200 的**非线性**表(第 10 个攻击者开始直接给到 1200)。
   要点是**非线性**:两个人攻王和三个人攻王不是线性关系。我们只有一个线性王盾。
4. **易位权作为显式项**:已易位 +28,丢王翼权 −39、丢后翼权 −24(王翼更贵)。
   零成本,而我们的 PST 对"王还在中路"只有一点隐式惩罚。

**Wasabi 明确没有、但我们也不必因此不做的**:它没有 THREAT、没有 SPACE、没有单独特化的残局知识
(除了"无兵和棋阈值")。所以 Wasabi 是"最小可用的强 HCE",不是上限。

## 三、从 SF 11 经典估值借什么(Wasabi 也没有的那些)

1. **IMBALANCE(子力不平衡,`material.cpp` 的 `QuadraticOurs`/`QuadraticTheirs`)**
   子力价值**依赖棋盘上还有什么**。例如:双车协同、象对、双轻子换一车的补偿、多兵的"兵海"价值。
   我们现在只有一条扁平的"双象 +45"。这是"用很少的参数换很多知识"的典型:
   两张 21 个数的表,覆盖了所有子力组合的交互项。
2. **THREAT(威胁,SF 里最大的一块现代 HCE 知识)**
   按"攻击者类型的威胁"给分:轻子威胁、车威胁、兵威胁、挂子(hanging)、过载(overloaded)、
   穿过王翼的长斜线的象、被自己的子挡住的子。它的 `ThreatByMinor[PIECE_TYPE_NB]` /
   `ThreatByRook[PIECE_TYPE_NB]` 是**一维 6 项**(按"被攻击的子"索引,每项含 MG/EG,各只 12 个数):
   轻子威胁后 = `S(79,161)`、车威胁后 = `S(51,38)`、车威胁马 = `S(38,71)` ——
   **十几个数就表达了"什么子威胁什么子值多少"这一整张知识表。**
   **这是 Wasabi 完全没有的一整类知识。**
3. **KING safety 做全**:攻击者权重按子类型 ——
   `KingAttackWeights[PIECE_TYPE_NB] = { 0, 0, 81, 52, 44, 10 }`,即
   **马 81 > 象 52 > 车 44 > 后 10**。反直觉但合理:后的攻击是"预期之内"的,马的攻击最难防备,
   所以马权重最高、**后反而最低**。再叠加每个攻击者的**安全将军**格数
   (`KnightSafeCheck` / `BishopSafeCheck` / `RookSafeCheck` / `QueenSafeCheck`)、
   king ring 被攻击计数、侧翼攻击、以及**王前盾 + 攻击风暴**(`ShelterStrength` / `UnblockedStorm`)。
4. **SPACE**:只在中局、把"我方兵后方的空位"按区域计分。对封闭局面的判断几乎免费。
5. **INITIATIVE / tempo**:`constexpr Value Tempo = Value(28);`(`evaluate.h`,约 1/3 个兵),
   而且在 `search.cpp` 里以 `+ 2 * Tempo` 施加 —— **挂在搜索层,不在 `evaluate()` 里**
   (它刻画的是"轮到谁走"这个状态,不是局面本身)。我们完全没有 tempo 项 ——
   先手后手评估对称,而实战里先手值小半个兵。
6. **残局缩放因子(`endgame.cpp`)**:KXK / KBNK 是"理论赢但可以弃和"、异色象局面接近和、
   单兵残局的"兵在边线/车前兵=和"等。我们现在只有 `insufficientMaterial` 一项。
   **这是"避免把和棋走输"的知识,性价比很高。**
7. **子力值的二次项**:SF 的子力价值带一个"按该子数量缩放"的项(`v * (100 + x*count) / 100`),
   即第 2 个车的价值不等于第 1 个。我们用固定值。
8. **最重要的一条(结构,不是知识):PSQT 只存"半个棋盘"**
   SF 的 PSQT 声明是 `Bonus[][RANK_NB][int(FILE_NB)/2]` —— **只存 4 个半列**,另 4 列靠左右镜像生成。
   我们的 PST 是 6 张表 × 64 格 × 2 相位 = 768 个数,而**写出来的值本身就是左右对称的**:
   看我们的兵表 `55, 65, 65, 75, 80, 65, 65, 55` —— a 列与 h 列同值、b 列与 g 列同值,八张表都是这样。
   也就是说 **768 个自变量里有一半是重复的**。手写时这只是"多打几个字";但到 §五 调参时它是真问题:
   **在一个一半维度都退化的空间里做优化,等于把一半的数据和算力浪费掉**,而且对称的那两个参数
   会被优化器拉向不同方向,凭空制造噪声。**先把表达改成不冗余的(768 → 384),再谈调参** ——
   这是零成本、零风险的收益(§六 阶段 1)。

## 四、⚠️ 许可证:两个参照物都不能抄数值

这一节必须放在实现之前,因为它直接决定"照抄"这条路走不通。

| 项目 | 许可证 | 我们 |
|---|---|---|
| **Stockfish**(官方仓库) | **GPL-3.0** | MIT |
| **Wasabi**(`mhonert/chess`) | **GPL-3.0** | MIT |
| 本仓库 | `package.json` 声明 **MIT**(根目录暂无 LICENSE 文件) | — |

**可以做**:阅读源码、理解算法、借鉴**结构与方法**(思路、公式形式、项该怎么组合)。
著作权保护表达,不保护思想;照结构自己实现,不构成侵权。

**不可以做**:把它的**参数数值表**搬进我们的代码。数值表是"表达"的一部分;
整表复制(或逐值抄录后微调)会构成**派生作品**,而 GPL-3.0 具传染性 ——
一旦并入并分发,整个 WebOS 需要以 GPL-3.0 提供源码。这与 §4.6 里对 Wasabi 的判断是同一条硬线。

**那数值从哪来 —— 三条路,按推荐度排序:**

1. **自己调参(推荐,也是唯一能把那 190 Elo 真正赚回来的路)**
   见 §五。这也是 Wasabi 和 SF 自己做的事:SF 用 SPSA 迭代了多年,Wasabi 用 Zurichess 的 725k 局面。
   **参数值本身不是资产,"能生成参数值的流程"才是。**
2. **用有明确出处的公开表**:PeSTO(Ronald Friederich,公开在 TalkChess / 国际象棋编程维基)
   是这类表的通用参照。注意它**同样是从 Stockfish 派生调参**来的,严格说仍在灰区 ——
   要用就注明出处,但要明白它不比"自己调"更干净。
3. **不引入任何第三方数值**,只按 §二/§三 加项,数值先用教科书量级的手写值。
   这能验证"机制是否有效",但拿不到调参带来的全部收益 —— 因为参数不准,加项本身也可能**帮倒忙**
   (加了一堆权重错的项,可能比不加更弱)。

> 我的判断:**先做 1 的准备工作(写调参器),同时用 3 的数值先落地骨架**。
> 这样代码结构先立起来,调参器一就绪就能立刻产出数值。

## 五、参数值从哪来:一个够用的调参器

> ⚠️ **本节已被 `docs/chess-eval-tuning-plan.md` 取代,保留作历史记录。**
> 两处结论要更正:
> 1. **不用坐标下降、也不用 SPSA。** 我们的评估在参数上是**严格线性**的,所以这是**线性最小二乘**,
>    有闭式解 `w = (ΦᵀΦ + λI)⁻¹Φᵀy` —— 凸问题,坐标下降是严格更差的选择。
> 2. **数据已经就位,而且是 SF 标签而不是对局结果**:`tuner/sample-dataset.mjs`
>    已产出 `data/train.jsonl`(30.7 万)+ `val.jsonl`(3 万),标签是 Stockfish 的 cp/mate。
>    所以目标是**监督蒸馏**(逼近 SF 的评估),不是 Texel 式的"拟合对局胜负"。
>
> 下面这段是原计划,仅作对照。

不需要 GPU,也不需要 725k 局面起步。Texel 风格的调参在我们这个规模上很现实:

- **数据**:用本引擎自我对弈产出局面 + 结局(胜/和/负),或者用公开的 PGN 局面库。
  目标是每个待调参数有 ~1000 个局面量级 → 300 个参数需要 ~30 万局面。
  自我对弈 30 万局面在 Node 单线程上是可以跑完的(本引擎 ≈41~49 万 NPS)。
- **目标函数**:`min Σ (结果 - sigmoid(评估值 / K))²`(K 是缩放常数,约 1.0~1.5 兵),
  即让"评估分数"去拟合"实际对局结果"。这就是 Texel 的方法。
- **优化器**:坐标下降(coordinate descent)先跑起来最省事 —— 一次只动一个参数,
  接受让误差下降的改动;或者直接用随机梯度下降。**不需要什么高级优化器,需要的是数据量。**
- **实现要点**:
  - 参数要能**批量重新计算**(把参数抽成一个 `EVAL_PARAMS` 对象,调参器直接改这个对象);
  - 评估要**可增量**:只重算受影响的项,否则 30 万局 × 每局几十个局面会慢到不可用;
  - 必须**留出验证集**,拿训练集上降下来的误差去验证集上确认,否则就是过拟合。

## 六、分阶段实施 + 验收标准

每个阶段都能独立验收,且**验收不需要任何第三方引擎**(`bench/vendor/` 现在是空的):

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **0** | 把评估参数抽成独立的 `EVAL_PARAMS` 结构(纯重构,数值一个不改) | `chess-engine-test.mjs` **67/67 仍全过**;且"新旧评估逐局面分数一致" —— 重构不许改变任何棋力 |
| **1** | 加项:机动性(安全机动性)、通路兵、易位权、tempo;PST 按半列镜像**去冗余**(768 → 384) | ① 同上 67/67;② **A/B 自对弈**:新评估 vs 当前评估,确定性节点预算打 ≥200 局,**得分率 > 52%** |
| **2** | 加项:王区威胁(非线性攻击者表)、IMBALANCE、THREAT、SPACE | 同上 A/B 得分率再涨;体积闸门 ≤35 KB 未被突破 |
| **3** | 写调参器;先用自我对弈数据把阶段 1+2 的参数调一遍 | 验证集误差显著下降;A/B 得分率继续涨 |
| **4** | 对外标定:重跑 `bench/uci-bench.mjs` 的交叉深度 | **hard 档交叉深度从 SF d7.34 提升到 ≥ d8.0**(≈ +50 Elo 量级) |

**为什么 A/B 自对弈是这一整条路的正确验收手段**:双方都是我们自己的引擎、都给节点预算,
所以它对第三方引擎零依赖(当前 vendor 空着也不影响)、完全可复现、而且直接回答
"新的评估是不是真的更强" —— 比拿它去和别人打更干净(没有对手强度噪声)。

## 七、明确不做

- **不碰 NNUE**:理由见 `chess-ai-plan.md` §3.7(JS 标量执行会把 NPS 打下去一个数量级)。
  本方案的目标是"把手写 HCE 做到它该有的水平",不是换技术路线。
- **不引入第三方参数表**(§四)。这也意味着**不要**照抄 Wasabi 那张 `KING_DANGER_PIECE_PENALTY`。
- **不做开局库**:与体积约束冲突(Wasabi 那份数据文件 369 KB,比我们整个引擎大 60 倍)。
- **不在阶段 1/2 就动 PST 的数值**。PST 的数值该由阶段 3 的调参器产出,
  手改 PST 是"凭感觉调参",正是我们要避免的事。阶段 1 只做**去冗余**(减半自变量,不改变表达力)。
