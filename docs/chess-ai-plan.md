## 一、起点:一段不像 AI 的 AI

改造前的 `js/apps/chess3d/index.js` 里 `aiMove()` 的全部决策逻辑:

```js
for (每个我能动的格子)
  for (每个合法着法)
    score = (吃到的子 ? VAL[t] * 10 : 0) + Math.random() * 3
    if (送到被子攻击的格子) score += 2
  取 score 最高的一步
```

三个致命缺陷:

1. **只看一层**。对手下一步反吃完全看不见,「送后」「叉子」这类陷阱一个都躲不掉。
2. **没有静态搜索**。搜索到深度上限时若正处在换子中途(刚吃掉一个兵、自己的后正被攻击),
   评估会把这个「未结算」的局面当成终局,得出完全错误的结论 —— 这就是地平线效应。
3. **随机数直接参与决策**。`Math.random() * 3` 与一个兵的价值同量级,导致 AI 每步的
   判断标准都不一致,表现像一个发挥极不稳定的新手。

此外 `applyMove()` 每次 `cloneB()` 深拷贝整个棋盘,搜索中每节点一次全盘拷贝,是纯粹的性能浪费。

**棋规引擎本身是对的**(perft 级别验证过基本走子、易位、吃过路兵),所以这次是
**换掉引擎内部的搜索与评估,不是重写规则** —— 这条边界由 perft 守住。

## 二、档位设计:用节点预算,不用墙上时间

原方案打算按「思考时间预算」分档(50ms / 400ms / 1.5s / 4s)。**实测后改为以节点预算为主、
时间只作兜底**,理由有三:

- 时间预算在不同设备上棋力会漂移,同一个「1.5s」在快机上是 9 层、慢机上可能只有 5 层;
- 节点预算是**设备无关、可复现**的,同一局面必然得到同一着法;
- 于是测试可以断言「这个局面在 N 节点内必须找到正解」,AI 的回归测试变成确定性的 ——
  这也是后面所有对局基准能用 `--shard` 并行分片而不影响结果的前提。

| 档位 | 节点预算 | 时间兜底 | 实测深度(开局/意大利/中局/残局) | 耗时 |
|---|---|---|---|---|
| 初级 easy | —(见下) | 200ms | 2 / 2 / 2 / 2 | 0.01 ~ 0.04s |
| 中级 normal | 40k | 500ms | 7 / 7 / 6 / 8 | 0.10 ~ 0.16s |
| **高级 hard(默认)** | **160k** | 900ms | 9 / 8 / 9 / 10 | 0.31 ~ 0.39s |
| 大师 master | 1.2M | 3.5s | 11 / 10 / 11 / 13 | 2.8 ~ 3.4s |

对比最初「中级 5~6 层 / 高级 6~8 层 / 大师 8~10 层」的预估,**每一档都超出**。
NPS ≈ 41 ~ 49 万节点(Node 单线程;浏览器 JIT 热起来后更高)。

> ⚠️ **初级档不走节点预算这条路**。它固定只搜 2 层,然后在「最优解 ±70cp」的着法池里
> 随机挑一个(见 §3.6)。它是**故意**做弱的,`nodes` / `ms` 对它不起作用,所以
> 「20k 节点」在实现里是个不生效的占位值。**在最优解附近随机**,而不是给评分加随机噪声 ——
> 前者弱得可控且同一局面表现一致,后者会让 AI 前后矛盾。

## 三、引擎设计

### 3.1 文件拆分与硬约束

改造前是一个 400 行的单体,Three.js 渲染和棋规搅在一起。按职责切开:

```
src/
  rules.js     棋规:走法生成、make/unmake、Zobrist 哈希
  ai.js        搜索(PVS/迭代加深/剪枝)+ 评估函数
  eval.js      评估参数与特征(单一事实源,后续追加)
  worker.js    薄壳:{id,moves,nodes,ms,depth} → {id,move,depth,nodes,ms,score}
(3D UI 的 index.js 留在 webos 侧,瘦身后不含任何棋规/搜索逻辑)
test/engine-test.mjs   perft + 战术局面 + 与旧实现对拍
```

**硬性约束**:`rules.js` / `ai.js` / `ai-worker.js` 不得 import 渲染库、不得碰 DOM。
这一条带来两个好处:

1. Worker 可以直接 `import` 它们;
2. `tools/*.mjs` 能在 **Node 里直接跑**,不用开浏览器就能做 perft、战术测试和**对局基准** ——
   这是整个方案里性价比最高的一条,后面 §9.5 的全部棋力数据都建立在它上面。

`check-size.mjs` 会把这条约束写成断言:引擎 chunk 里出现 `gl_FragColor` 等渲染指纹即失败。

### 3.2 内部表示:Int8Array mailbox + make/unmake + Zobrist

> 最初打算「保留现有 `board[r][c] = {t, c}` 对象语义以便回归对比」。**这是个错误的取舍** ——
> 对象数组在搜索热路径上会成为 JS 版最大的性能瓶颈。改为下面的平坦表示,
> 旧实现只作为测试里的答案参照(oracle)留存。

- **棋盘**:`Int8Array(64)` mailbox,棋子编码成小整数(`(color<<3)|type`,0 表示空格)。
- **棋子列表**:每色一个 `Int8Array(16)` 存格号 + 格子→下标的反向表。遍历己方棋子不必扫满 64 格。
- **走法**:单个 int32 打包(起点 / 终点 / 吃子 / 升变 / 易位标志位),每层预分配
  `Int32Array(256)` 缓冲区。**搜索全程零对象分配** —— 这是 JS 引擎特有的收益:
  没有分配就没有 GC,没有 GC 就不会在思考中途随机掉帧。
- **make/unmake**:原地修改 + undo 栈(扁平 typed array),不再 `cloneB`。
  undo 记录:被吃子、原 castle 权、原 ep、是否易位/升变。
- **Zobrist 哈希**:每格 × 12 种棋子一个随机数(mulberry32 生成,与黑白棋 `index.js` 同源),
  外加走子权、8 个 ep 文件、16 种 castle 权,增量 XOR 更新。两个用途:
  - **置换表**:2^20 槽,存 key / 深度 / score / flag(EXACT \| LOWER \| UPPER)/ 最佳着法。
  - **重复局面检测**:既判对局历史,也判**搜索路径内**的重复(后者是从 chessy 学来的,§4.5)。

### 3.3 搜索

沿用黑白棋已验证的骨架(PVS 负极大 + 迭代加深),补充象棋专属的部分:

- **α-β / PVS**:主变全窗口搜,其余用零窗口探测,失败再重搜。
- **静态搜索(quiescence)**:叶子节点的分数不可信,必须沿「吃子 + 升变」继续展开到局面安静。
  这是**修复地平线效应唯一有效的手段**,也是本次升级里性价比最高的一项。配 δ 剪枝 +
  简单的 SEE 过滤掉明显亏本的吃子。
- **走法排序**:TT 最佳着法 → 吃子按 MVV-LVA → killer moves → history 启发式。
  排序质量通常能换来 1~2 层实际深度,比优化评估函数更值。
- **将军延伸**:被将军时 depth + 1(限总延伸次数),避免最典型的那类失误 ——
  在被连续追杀时,搜索边界正好卡在杀棋前一步。
- **终局处理**:将死返回 `-(MATE - ply)`,逼和返回 0。带 ply 是为了让 AI 在多个杀法中
  **选最短的那个**,而不是把对手遛一整局。

### 3.4 评估函数

从「吃掉什么」升级为「局面好不好」。**实现里实际只有下面 6 项**(列清楚,免得读者高估):

| 项 | 实现 |
|---|---|
| **子力** | `VAL_MG = p100 n320 b330 r500 q900`,残局表 `p110 n310 b330 r550 q950` |
| **PST** | 6 张中局表 + 6 张残局表(兵/马/象/车/后/王),白方视角书写,黑方 `s ^ 56` 镜像 |
| **相位插值** | 相位权重 `N1 B1 R2 Q4`(兵不计),`PHASE_MAX = 24`;按 `(mg·phase + eg·(24−phase))/24` 混合 |
| **兵结构** | 只有**叠兵**(mg −12/个、eg −22)与**孤立兵**(mg −14、eg −16) |
| **王盾** | `phase > 8` 时数王前方 3 个文件的己方兵,缺一个 mg −14 |
| **双象** | mg +25 / eg +45 |

**明确没有的**:mobility(子力机动性)、**通路兵 / 落后兵**、开放线、**王区攻击者计数**、升变前景、空间。
也就是说本引擎的位置知识**几乎全部由手写的 PST 承载** —— 而 PST 是静态的,
同一个格子上的马被自己兵堵死还是畅通无阻,评分完全一样。这是 §9.5.6 里我们"节点不值钱"的根因。

调参说明:PST 取自社区通用取值,**没有做过任何自动调参** —— 这一点不宣称做了。
**能对比的参照物是 §4.6 的 Wasabi**:它的**全部**评估参数(子力值、各子机动性表、兵结构、王安全)
都用 Zurichess 作者收集的 **725,000 个局面**做过回归调参(其 README 原文:
*"A set of 725000 test positions ... was used to tune all evaluation parameters"*),
这正是我们做不到的事,也是 §9.5.6 里它单位时间效率高我们一个数量级的主因之一。

**参数规模上我们其实更大,但还是更弱** —— 这一点值得单独记住:

| | 评估参数个数 | 怎么来的 |
|---|---|---|
| 本引擎 | **≈ 796**(其中 PST 占 768 = 6 张表 × 64 格 × 2 个相位) | 全部手写常数 |
| Wasabi | **≈ 165**(子力 10 + 机动性 132 + 王区威胁 16 + 标量 7) | 725,000 局面回归调参 |

**Wasabi 用不到我们 1/4 的参数打败了我们。** 它的机动性表尺寸不是拍脑袋定的,而是被棋的几何**决定死**的
—— 马最多 8 个落点 → 表长 9;象 13 → 14;车 14 → 15;后 27 → 28 —— 一档都不多余。
省下来的自由度全部投给了**数据**:每 1 个参数背后约 **4,400** 个调参局面。
我们是反过来的:自由度过剩(796 个手写数字,其中没有任何一个被验证过),数据为 0。

> 顺带破一个容易混淆的量:它 370 KB 的 wasm **不是被评估参数撑大的** —— 165 个 i32 值只有几百字节,
> 体积主要来自引擎代码和仓库里那份 369 KB 的开局库数据文件(§4.6)。
> 所以"体积大"和"评估参数多"在这里是两件事,别混着读。

> **下一步怎么改评估函数** —— 照 Wasabi / SF 旧版经典估值该怎么借、参数值从哪来、
> 以及**为什么两者的参数一个都不能抄**(都是 GPL-3.0,我们是 MIT),
> 见独立文档 **[`docs/chess-eval-upgrade.md`](./chess-eval-upgrade.md)**。

### 3.5 不卡 UI:Web Worker

| 方案 | 评价 |
|---|---|
| **Worker** ✅ | 采用。UI 侧改造成本很低:引擎是纯 JS 模块,Worker 直接 import。`postMessage` 只传走法序列与节点预算,不传棋盘对象。代价是异步化要处理「AI 思考时用户开了新对局/换档/关窗」的竞争条件 —— 用请求自增 id 丢弃过期结果即可。 |
| 主线程分段 `await yieldUI()` | 黑白棋现有做法,改动最小,但预算只能给到 300~600ms 否则每帧卡顿能感觉到。 |
| Worker + 降级 | 两份代码路径,调试成本翻倍,不做。 |

Worker 还带来一个额外好处:**将来换 WASM 时天然就在正确的位置**,UI 线程完全不受影响。

> 实现细节:Worker 里的搜索是同步跑的,消息只会排队 —— **要真中断只能 `terminate()` 再新建**
> (新对局 / 换档 / 关窗),日常靠 id 丢弃过期结果即可。

### 3.6 UI 联动

- 工具栏「人机:开」按钮 → 升级为**难度下拉**(初级 / 中级 / 高级 / 大师),默认高级。
  实测可在 4 档间任意跳且与引擎状态同步。
- 状态栏右侧显示实时搜索信息:`深度 6 · 128kN · 0.8s · +0.7`。
- 思考中有明确提示,且**搜索期间拖拽改视角与滚轮缩放继续生效**(实测大师档 2.9s 搜索期间
  主线程出帧 198 次,theta 0→0.96、radius 13→11.8 均生效)。
- **兼容保障**:`window.__chess` 的 `click` / `turn` / `board` 三个钩子签名不变,
  `tools/e2e.mjs` 的 T33.2 用例不受影响;新增信息只追加到 `stats()` 的 AI 字段。

### 3.7 剪枝增强:同预算下真正拉开差距的那几项

只写教科书主干(PVS + TT + 排序 + 静态搜索)是不够的。**同一个 CPU 预算下,
下面这几项带来的收益远大于调评估参数:**

| 技术 | 干的事 | 相对收益 | 实现成本 | 坑 |
|---|---|---|---|---|
| **空着剪枝 Null-move** | 轮到自己走但存在 β 以上的静态分时,直接「不走这步」搜浅一层 | **最高**,通常 +1~2 层 | 低(约 30 行) | 残局只有王兵时必须关掉(zugzwang 会误判) |
| **迟着裁减 LMR** | 排序靠后的安静着法自动减一层,引发 α 提升再补搜 | 高,+1 层以上 | 低 | 参数敏感(pv / 被将军 / 吃子 / 升变都要例外) |
| **Aspiration window** | 迭代加深时用上一层分数 ±50 开局窗口,而非全窗口 | 中,省下大量重搜 | 极低 | 窗口失败要放宽重搜 |
| **Reverse futility / futility** | 明显追不上 α 的着法直接剪掉 | 中 | 低 | 别在有将军可能的局面启用;要配 *mate distance* 保护 |
| **History / continuation history** | 取代简单 killer,按着法在兄弟节点中的历史表现排序 | 中到高 | 中 | 表很大,要用 `Int32Array` 并做归一化,否则 GC 咬回来 |
| **静态搜索内 SEE 过滤 + δ 剪枝** | 进 qsearch 前判断这个交换是否明显亏本 | 中 | 中 | SEE 写错会直接漏战术,必须用单测守住 |
| **延伸:将军 / 吃回** | 将军时 +1 层 | 中(主要消除边界假窗口) | 低 | 延伸总量必须封顶,否则深度爆炸 |

**收益排序总结:「怎么搜索」比「怎么评估」更值钱。** 在 5~8 层的浅搜索里战术能力主导棋力,
精力应优先砸在搜索侧;评估函数的边际收益要到 10 层以上才明显上升。

反过来,以下几件在这个预算下**不划算**(写清楚以免后面又想做):

- **JS 版 NNUE**:NNUE 的强度来自「每个 Eval 用几十万次 int8 乘加换来的精度」,C++ 里靠
  AVX/SIMD 摊薄到几微秒;JS 是标量执行,同样的推断会把 NPS 打下去一个数量级,大概率净亏损。
- **MCTS(AlphaZero 那条路)**:没有策略/价值网络就没有 prior,MCTS 退化成随机模拟,
  同等预算下远弱于 α-β。这条路要 GPU,与「3D 网页小游戏」场景无关。
- **MTD(f)**:依赖极好的置换表与稳定评估,在 PST + 大写表命中率不足时收益不稳定,
  与 PVS + aspiration 基本持平,不值得多担复杂度。
- **终局残子库**:文件体积动辄几十 MB,违反项目资源约束。

## 四、WASM 路线评估

你提了 WASM,这部分算过账。**结论:不作为第一阶段,且实测后判定当前不需要启动。**

### 4.1 前置成本(实测本机状态)

```
cargo / rustc / rustup      未安装
wasm-pack / emscripten      未安装
clang / wat2wasm            未安装
```

走 Rust-to-WASM 需要先装 rustup + Rust 工具链 + `wasm32-unknown-unknown` target +
`wasm-bindgen`,以及 `wasm-opt`(否则产物偏大)。这是一笔几百 MB 到上 GB 的安装量,
而且**每个贡献者都要重复付出**。

> **但有例外**:§4.6 的 Wasabi 证明 **AssemblyScript 是纯 npm 工具链**(`npm i -D assemblyscript` + `asc`),
> 不需要任何额外 SDK。所以「上 WASM 必须装 Rust」这个论断只对 Rust 成立。
> 将来真要上 WASM,**优先评估 AssemblyScript 而不是 Rust** ——
> TS 语法、零额外 SDK、构建能直接并入 `npm run build`。

### 4.2 收益

WASM 版可以用真正的 u64 位棋盘 + 完全无 GC 的数据结构。相对优化过的 JS:

| 指标 | 纯 JS(带 make/unmake) | Rust → WASM |
|---|---|---|
| 预期 NPS | 约 5万 ~ 20万 | 约 30万 ~ 100万 |
| 同等时间预算下的额外深度 | — | **大约 +1 ~ 2 层** |
| 确定性 | 依赖 JIT,有 deopt 风险 | 稳定 |

> 这些数字是位棋盘 vs 对象数组的经验估计。**实测比预期保守得多**:本引擎实测 NPS 已达
> 41~49 万(§2),而 §9.5.6 量到 Wasabi(361KB wasm,含调过参的评估)在同局面达到同强度
> 只要 25ms —— 它的优势主要来自**评估质量与削减质量**,而不是单纯的位棋盘速度。

### 4.3 成本

1. **二进制入仓库**:`.wasm` 文件 100~300KB,committed binary blob,review 时看不见内容变化。
2. **构建链路变长**:`npm run build` 不再够用,变成
   `cargo build --release && wasm-bindgen && npm run build`(要写进 npm script 和 CI)。
   README 对外强调「无后端、产物丢到任意静态服务器即可运行」,引入 wasm 后产物会多出
   一个二进制文件(仍是静态文件),这条会被削弱。
3. **调试体验倒退**:浏览器断点打不进 Rust 源码(需要配 dwarf + 特定插件),
   回溯信息远不如 JS 直观。perft 调试会痛苦很多。
4. **贡献门槛**:以后任何人想改象棋 AI 的一条评估规则,都要先装 Rust。

### 4.4 结论与决策规则

**决策路径:先做阶段一(纯 JS + Worker),把接口层抽干净。WASM 作为可选项,用实测数据判定。**

判定规则(原定,现已执行):

- 若高级档仍**达不到稳定 6 层**,且瓶颈是搜索速度而非评估质量 → 再谈 WASM。
- 若已能稳定 6~8 层,WASM 换来的 1~2 层对「3D 休闲对弈」几乎无感 → 不值得引入 Rust 工具链。

**执行结果:高级档实测 8~10 层、大师档 10~13 层,远超阈值 ⇒ 不启动阶段五。**
所以本方案为 WASM 留下的真正遗产是**接口层**:如果将来要换,
推荐形态是「引擎 → 放进现有 Worker → 通过统一 `engineApi`(与 JS 版签名完全一致)切换」,
替换成本很低。

### 4.5 开源方案一:chessy(`den-run-ai/chessy`,MIT)

核实过的事实(2026-09-17):

| 项目 | 实测结果 |

| Star / Watch | **1 / 0**;创建于 2026-07-15,最后推送 2026-09-16;29 个开放 issue |

**它有什么**(读 `search.rs` 确认):Zobrist 置换表、`quiesce_node` 静态搜索、
history/killer 排序(`record_quiet_cutoff`)、MVV-LVA(不叫这个名字,但
`search.rs` 641~642 行的 `+ 10 * ordering_value(被吃子) - ordering_value(攻击子)` 就是标准公式)、
节点预算闸门、搜索路径重复检测(`check_node_repetition`)、insufficient material 处理。

**它没有什么**:空着剪枝 0 处、LMR/reduction 0 处、futility/razor 0 处、aspiration 0 处。

**结论:不引入依赖,但把它当参考实现。** 三条理由:

1. **它是整机 App,不是库**。要用得把 wasm 和它的 `wasm-engine.js` loader 剥出来适配裸 ABI,
   还得自己解 `window.__chess` 那套 Board↔ABI 转换。省下的代码量没有看上去那么多。
2. **上游风险**。1 star / 0 watch / 29 issue / 仓库里 20KB 的 `CLAUDE.md` 与 `AGENTS.md`
   (典型的 agent 驱动开发痕迹)。冻结一个 third-party 二进制,等于把 bus factor 交出去。
3. **强度上没有便宜可占** —— 实测同预算打平,见下。

> **实测回填**:原本判断「它的强度天花板 ≈ 本方案减去那四项剪枝,引入它等于换个更低的天花板」。
> 实测**推翻了这个判断**:同节点预算(160k : 160k)下双方 **6:6 打平**,且 chessy 达到同一强度
> 只要 204ms、我们要 389ms(`≈1.9×` 快)。那四项剪枝没能在实战里拉开差距 ——
> 真正拉开差距的是**评估函数质量**(它是 PeSTO 调参值)。这也正好印证了 §3.7 的结论:
> 在这个深度区间,瓶颈已经从「看得不够深」变成「看得再深也评不准」。
> **结论本身不变**(不引入依赖、当参考实现),它确实做到了「用一个更低的上游天花板换取省事」,
> 而在我们这边写并不比读它更难。

**要从它那里拿走的做法**(这几点确实更好,已并入实现):

| 采纳项 | 为什么更好 |
|---|---|
| **用「节点上限」而不是「墙上时间」做难度预算** | 见 §二。原「ms 预算表」改为「节点上限为主 + 时间兜底」。 |
| **搜索路径内的重复局面也记 0 分**(不只对局历史) | 让 AI 在赢棋时主动避开重复、输棋时奔向长将。即它的 `root_completed_threefold` + `check_node_repetition`。 |
| **低难度档用「在最优解 N 分以内随机挑」代替「给评分加随机噪声」** | 加噪声会让 AI 同局面表现前后不一致;在 root 挑相近着法才是正统做法,弱得可控又不离谱。即它的 `shuffle_root`。 |
| **复用它的 perft 标准局面与 insufficient-material 规则表** | 测试局面覆盖比手写更全。 |

附:我们的 perft 标准值(fixture 直接取标准局面)。
初始局面 **20 / 400 / 8902 / 197281**;Kiwipete **48 / 2039 / 97862 / 4085603**;
局面3 **14 / 191 / 2812 / 43238**;局面4 **6 / 264 / 9467 / 422333**。

### 4.6 开源方案二:Wasabi(`mhonert/chess`)—— 技术参考价值最高,但许可证是硬门槛

核实过的事实(2026-09-17):

| 项目 | 实测结果 |
|---|---|
| 形态 | AssemblyScript(TS 语法 → WASM)写的国际象棋引擎 + React 前端 |
| Star / 活跃度 | **108 star**;2019-11 建仓;**最后推送 2024-04-23**(约两年半未动);最近 release v1.5.0 在 **2020-07** |
| 许可证 | **GPL-3.0-or-later**(我们项目是 MIT) |
| 预编译产物 | 仓库内无 wasm;release 附 `wasabi-v1.5.0-engine.wasm` **370 KB** |
| 构建方式 | `npm i -D assemblyscript` + `asc`(**纯 npm 工具链,不要 Rust**) |
| 评估 | 参数用 Zurichess 的 **725,000** 局面做过回归调参 —— 我们明确做不到的事 |
| 其他 | 6 档难度、FICS 对局生成的开局库(数据文件 369 KB) |

**它有什么**(读 `assembly/engine.ts`,893 行实证):空着剪枝、迟着裁减、futility、
静态搜索 quiescence、SEE、历史启发式、Zobrist 置换表、PV、**razoring**
(`const RAZOR_MARGIN: i32 = 130;` 与 `else if (depth == 1 && getScore() * playerColor < alpha - RAZOR_MARGIN)`,
是活跃分支不是注释残留)。

**它没有什么**:aspiration window、δ 剪枝、将军延伸。

**结论:**

1. **许可证是硬门槛,不是技术取舍。** GPL-3.0 与我们的 MIT 项目不兼容:把它的源码或编译产物
   并入并分发,整体作品需要以 GPL-3.0 提供源码。要开这条路得先把整个 WebOS 项目改成 GPL-3.0 ——
   这是产权决定,不是技术决定。
2. **可以读,不可以抄。** GPL 不禁止阅读与借鉴思路,但逐行翻译到近乎一致的实现有「派生作品」风险。
   正确用法是拿它当**行为规格**:验证技术清单、核对边界条件。
3. **它反过来确认了 §3.7 是对的。** 一个 108 star、有真实用户、评估调过参的引擎,用的正是
   「空着剪枝 + LMR + futility + 静态搜索 + SEE + 历史启发式」这套。这套是这类引擎的
   **共识底线**,我们不该低于这个配置 —— 我们最终也确实实现了它(缺的只有 razor/aspiration 这类纯加速项)。

**两个参考项目对照:**

| | chessy | Wasabi |
|---|---|---|
| 产物体积 | 37 KB | 370 KB |
| 许可证 | MIT(可自由用) | GPL-3.0(整合需改我方许可) |
| 引擎技术 | 缺空着剪枝 / LMR / futility | **四项齐全** |
| 评估 | PeSTO 公开值 | 725k 局面调参过 |
| 活跃度 | 1 star,在动 | 108 star,已停 |

值得注意:**两者都没有 aspiration**,印证了把它列为「中低收益、顺手再做」是合理的,不是漏项。

**三个引擎同台对打后,上面两张表的技术清单差异被量化了** ——

- **Wasabi 是三者里单位时间最强的一个**:它在 Stockfish 标尺上 ≈ SF d6.55(d6)/ d7.81(d8),
  而达到本引擎默认档的强度只要 **25ms**(本引擎要 389ms)。给它同样的 ~0.4s,它到 12 层,约 **+215 Elo**。
- **chessy 与本引擎同预算打平,但每单位时间快 ≈1.9×**。

所以这两张表应当这样读:**「四项齐全 + 调过参的评估」确实买到了实打实的强度**,
§4.6 结论 3 的判断被证实;**但结论 1 的取舍依然成立** —— 我们放弃的是约一个数量级的
单位时间效率,换来 MIT 干净许可与 6.2KB 的体积。完整数据在 §9.5。

## 七、体积预算:引擎产物 ≤ 35 KB

### 7.1 先说清楚 35 KB 约束落在谁头上

实测当前构建产物(`dist/assets/`):

| 产物 | 原始 | gzip |
|---|---|---|
| **`app-chess3d-*.js`** | **92.7 KB** | **29.9 KB** ← 渲染层(已换用 ogl,见 §7.6) |
| **`app-chess3d-worker-*.js`** ← 引擎 | **15.4 KB** | **6.0 KB** |
| `app-reversi-*.js`(黑白棋引擎+UI 全套) | 13.6 KB | 6.0 KB |
| `core-*.js` | 81.4 KB | 29.7 KB |
| `index-*.js` | 31.9 KB | 12.6 KB |

**结论:35 KB 不可能落在整个 `app-chess3d` 分包上** —— 它现在是 29.9 KB gzip 且几乎全是渲染层,
要求「整个分包 ≤ 35 KB」意味着渲染层只剩 5 KB,除非放弃 3D,否则无解。

所以约束的合理解释是:**AI 引擎部分单独成块(放 Worker,自然独立成一个 chunk),
这个 chunk 的压缩后体积 ≤ 35 KB**。这也是唯一可执行的定义,下文按这个口径评估。

### 7.2 实测单价(用于原始预估,现已不再需要外推)

用项目里已有的真实产物反推,而不是拍脑袋:

- `app-reversi-*.js`:775 行源码(含 UI)→ 12.9 KB minified / 5.3 KB gzip
  ⇒ **minified 约 17 B/行,gzip 约 7 B/行**(Vite + terser 真实产物)
- PST 数据(12 棋子 × 64 格 × 中局/残局 = 3072 个值)实测:数组字面量 5.2 KB 原始 / 2.2 KB gzip;
  紧凑字符串编码 3.2 KB / 2.1 KB gzip(**gzip 后几乎无差别**),所以按可读性选了数组字面量。

### 7.3 实测结果(数字已钉死)

`npm run build` 后由 `tools/check-size.mjs` 直接量 gzip(level 9),不再外推:

| 模块 | 源码行数 | 源码字节 | 备注 |
|---|---|---|---|
| `rules.js` | 483 | 18,425 | 棋规 + make/unmake + Zobrist + replayMoves |
| `ai.js` | 608 | 23,973 | 搜索 + 剪枝 + SEE + 评估(含 PST 表数据) |
| `ai-worker.js` | 41 | 1,543 | 薄壳 |
| **合计(源码)** | **1,132** | **43,941** | — |
| **打包后 chunk** | — | **15,446 raw / 6,179 gzip** | **占 35 KB 预算的 17.2%** |

**比最初预估(9.0 KB gzip)还低 31%。** 原因找到了:预估用的「7 B/行」单价是从黑白棋量的,
而黑白棋源码里中文注释占比远低于本引擎 —— 本引擎 43.9 KB 源码里有大量「为什么这么做 /
踩过什么坑」的中文注释,压缩时被整体剥掉,产物只占源码的 35%。
**估计这类体积时,注释密度是比行数更强的自变量。**

> 余量:gzip 口径下 29 KB,minified 原始字节口径下 19.5 KB。§7.5 的降级顺序**一条都不需要动用**。
> 但也不建议为「把预算用满」而加评估项 —— §3.7 已论证过,这个深度区间里搜索侧收益远大于评估侧,
> 而 §3.7 列的技术已全部实现。

### 7.4 让约束可执行:体积门禁

不靠自觉。`tools/check-size.mjs` 在构建后遍历 `dist/assets/`,找到引擎 worker chunk,
gzip 后超过 35 KB 即非零退出,挂在 `npm run build` 之后。**体积是被断言的,不是被希望的**
(`--budget 4` 负向验证过会 exit 1)。

### 7.5 万一超标的降级顺序(按性价比从先砍到后砍)

1. 砍开局库(本来就没计划;Wasabi 那份数据 369 KB,绝对不能要)
2. 砍 SAN / FEN 解析 —— Worker 协议只传走法序列和节点预算,不需要完整记谱
3. PST 改紧凑字符串编码(minified 省 2 KB,gzip 省 0.1 KB)
4. 评估项做减法:评估一共只有 6 项(§3.4),从最贵的王盾下手,保留子力 / PST / 兵结构
5. 砍 futility / razoring 这类纯加速项(**静态搜索不能砍**,它关系到正确性,不是性能项)

### 7.6 附:three.js → ogl 换库(已执行 ✅)

**动机**:最初 `app-chess3d` chunk 是 **460 KB / 116.2 KB gzip**,其中约 110 KB 是 three.js。
即使按 §7.1 的口径这条约束不落在渲染层,把一个 116 KB 的库塞进一个小游戏也不合理。全部为实测:

| 方案 | 原始 | gzip | 说明 |
|---|---|---|---|
| three r160 现状 | 460.0 KB | **116.2 KB** | — |
| three **按需引入**(只 import 实际用到的 16 个类) | 460.0 KB | **116.2 KB** | **tree-shaking 完全无效**:`WebGLRenderer` 会把整个渲染器(着色器块/材质/光照)拖进来 |
| **ogl**(按需 11 类) | 50.8 KB | **14.9 KB** | ESM 源码分发,可 tree-shake |
| **ogl** 完整需求集(再加 Plane/Orbit/Raycast/**Shadow**/Mat4) | 73.4 KB | **21.0 KB** | 有真实阴影模块,能力基本对齐 |
| zdog | 29 KB | **7 KB** | 伪 3D(Canvas/SVG),**无光照无阴影**,视觉风格完全不同 |
| twgl.js | 388 KB | 73 KB | 太大 |
| regl | 293 KB | 60 KB | 太大 |
| 纯手写 WebGL | — | 约 3~5 KB | 需自己写约 400~700 行,并失去依赖维护 |

**ogl 与 three 的能力对照**(chess3d 用到的东西都有对应):
`Scene`→`Transform`(根节点)、`PerspectiveCamera`→`Camera`、`WebGLRenderer`→`Renderer`、
`Box/Cylinder/SphereGeometry`→`Box/Cylinder/Sphere`、`Raycaster`→`Raycast`、
`castShadow`/`shadowMap`→`Shadow`;唯一缺口是 `MeshStandardMaterial` + 灯光 ——
ogl 没有光照系统,自写了约 20 行 GLSL(一个方向光 + 环境光)。
自写的 theta/phi 轨道保留(省体积,也没必要换 `Orbit`)。

**执行结果**:three 已移除,换用 ogl 1.0.11。
`app-chess3d` chunk **460 KB / 116.2 KB gzip → 换库当时量到 80.7 KB / 24.8 KB**,
后续 UI 与引擎改动又增长了一点,**当前为 92.7 KB / 29.9 KB gzip**(约 3.9× 缩小)。
渲染 + 真实阴影 + 点击拾取 + 走子/AI 全部经无头 Chrome 探针验证通过,零控制台错误。

过程中修了两个 ogl 阴影特有的坑:

1. `Shadow` 自建 RenderTarget 默认 LINEAR 过滤,会插值破坏 RGBA 打包的深度 → 换 **NEAREST**;
2. 深度通道清屏色会混入场景背景色,导致只接收阴影的棋盘整体误判进阴影 →
   阴影 pass 前把清屏色改为白色(深度 1.0)。

点击拾取没有用 `Raycast.intersectBounds`(包围球对扁平方格会重叠),
改为**射线与棋盘平面求交 + 格子坐标换算**,更准也更小。

## 八、决策记录(原「需要你拍板」的最终落定)

1. **阶段一 ~ 四全部实施,阶段五不启动**(§4.4 的启动条件不满足)。
2. **默认档 = 高级**(`DEFAULT_LEVEL = 2`),以节点预算 **160k** 表达,实测 9 层 / 约 0.45s。
3. **保留初级档**,但不用「加评分噪声」,改为 §4.5 采纳的 **root jitter**(在最优解 ±70cp 内随机挑),
   弱得可控且同一局面表现一致。
4. **35 KB 口径 = 引擎 Worker chunk 的 gzip**(§7.1 的论证成立),因此这条约束**没有波及渲染层**;
   但渲染层仍独立完成了 three → ogl 换库(§7.6),`app-chess3d` chunk 现为 **92.7 KB raw / 29.9 KB gzip**。

### 9.4 两个必须记住的实现约定(踩过)

1. **走法有两套编码**:UI ↔ Worker 传输用线格式 `(from<<6)|to`(`replayMoves` 按此解析);
   引擎内部 `mkMove(from,to,flag,cap)` 是 `from` 在**低 6 位**。
2. **升变一律取升后**:`replayMoves` 只还原升后,所以 UI 拿到任何升变都必须先规整成升后
   (`index.js` 的 `normalize()`),否则本地局面与 Worker 重演出的局面会不一致。

### 9.5 棋力评估:≈ 2030 Elo

§9.2 只能说明「搜了几层」,证明不了「有多强」。这一节是真正回答强度的实测。

#### 9.5.1 方法

三个对弈级工具(见 §9.1)的共同前提是**双方都用确定性预算**:本引擎给节点数,
对手给 `go depth N` 或节点上限。因此每一局都可复现(改动驱动代码后,同一局仍得到
完全相同的 38 手被将杀),也就能用 `--shard` 分片并行而不影响结果。

对手:

- **Stockfish.js 10**(nmrugg 的 emscripten 构建,0.38MB)—— 作为「标尺」,
  因为固定深度 → Elo 有公开数据。
- **chessy**(§4.5,`den-run-ai/chessy` 的 Rust/WASM)—— **进程内直调它的 ABI**,不经任何中间引擎。
- **Wasabi**(§4.6,`mhonert/chess` 的 361KB wasm)—— 它是个 WASI standalone UCI 引擎,
  用 `@wasmer/wasi` 起在 Node 里就能当普通 UCI 引擎驱动。

> **运行时的三个坑**(都踩过,已写进工具):
> ① Wasabi 自带的 2020 年 WAVM 运行时在本机报 "Target X86 CPU does not support SSE 4.1" 直接跑不起来;
> ② `node:wasi` 会在首次 `fd_read` 上**段错误**;只有纯 JS 的 `@wasmer/wasi` 能用。
> ③ Wasabi 会吞掉 `sleep` 之后的第一条 `go`,且**不回复 `ucinewgame`** —— 所以每次
> `position` / `ucinewgame` 后都必须用 `isready`/`readyok` 做一次屏障。
> 另外 nmrugg 的 Stockfish.js 10 不能接受 `setoption name Threads`(会挂死)。

**Elo 锚点**:固定深度 N 的 Elo 用常被引用的那张表(Ferreira 2013,以 Houdini 1.5 锚定
depth-20 ≈ 2894 Elo,pawnalyze 沿用为 Stockfish 的近似值):

| SF depth | 5 | 6 | 7 | 8 | 9 | 10 | 12 |
|---|---|---|---|---|---|---|---|
| ≈ Elo | 1900 | 1966 | 2033 | 2099 | 2165 | 2231 | 2364 |

⚠️ 这是 2013 年的老数据,绝对 Elo 有 ±100 量级的不确定性(depth 1~5 那几档更是原表
按 ~66 Elo/层线性外推出来的)。**所以下面只把绝对 Elo 当「量级」,真正硬的是交叉深度和胜负。**

#### 9.5.2 本引擎四档 vs Stockfish 限深度

| 难度档 | 节点预算 | 局数 | 交叉 SF depth | ≈ Elo |
|---|---|---|---|---|
| 初级 easy | 2 层 + ±70cp 随机 | 48 | < 1(全程落于所有采样深度) | ≲ 1500 |
| 中级 normal | 40k | 136 | 6.39 | **1992** |
| **高级 hard(默认)** | 160k | 80 | **7.34** | **2055** |
| 大师 master | 1.2M | 18 | 8.39 | **2125** |

高级档的原始数据:

| SF depth | 局 | 胜 | 和 | 负 | 得分率 | Elo 差 | 95% 区间 |
|---|---|---|---|---|---|---|---|
| 6 | 24 | 14 | 1 | 9 | 60.4% | +73 | −64 ~ +241 |
| 7 | 20 | 13 | 0 | 7 | 65.0% | +108 | −41 ~ +314 |
| 8 | 24 | 3 | 5 | 16 | 22.9% | −211 | −475 ~ −72 |

(depth 7 比 depth 6 得分率还高,是采样噪声 —— 两者置信区间大幅重叠,不宜过度解读。)

**节点预算的性价比很低**:4 倍节点(40k→160k)只买到 ≈ 63 Elo;160k→1.2M(7.5 倍)
又只买到 ≈ 70 Elo。原因与 §3.7 的判断一致 —— 我们只上了 δ剪枝/SEE/空着削减/LMR 这一档,
评估还是「子力 + PST + 兵结构」的手写式子。**这时瓶颈已经从「看得不够深」转移到
「看得再深也评不准」,再堆节点几乎白费。**

#### 9.5.3 对 chessy(直接对局,同为节点预算)

| chessy 节点预算 | 局 | 胜 | 和 | 负 | 本引擎得分率 | Elo 差 | 95% 区间 |
|---|---|---|---|---|---|---|---|
| 40k | 12 | 10 | 1 | 1 | 87.5% | +338 | +137 ~ +1200 |
| 160k | 12 | 6 | 0 | 6 | **50.0%** | 0 | −223 ~ +223 |
| 640k | 12 | 4 | 4 | 4 | **50.0%** | 0 | −223 ~ +223 |

**同预算下打平**(160k : 160k = 6:6)。更有意思的是给 chessy 4 倍节点(640k)它**并没有变强**,
仍是 50% —— 它的深度只从 6 涨到 7,说明它同样被评估/剪枝质量卡住,不是被节点数卡住。
这与本引擎在 9.5.2 里「4 倍节点只买到 63 Elo」是同一个现象,**互相印证了这套引擎的瓶颈位置**。

⚠️ 口径说明:本引擎的 `nodes` **包含静态搜索节点**,而 chessy 的 `nodeLimit` 只算主搜索节点
(它的 `qnodes` 单独计数,开局实测占主节点量的 55%)。也就是说 chessy 在「160k」这个数下
实际做了**更多**的工作。**结论因此对本引擎是保守的。**

#### 9.5.4 对 Wasabi(直接对局,深度对深度)

| Wasabi 深度 | 局 | 胜 | 和 | 负 | 本引擎得分率 | Elo 差 | 95% 区间 |
|---|---|---|---|---|---|---|---|
| 4 | 12 | 11 | 0 | 1 | 91.7% | +417 | +201 ~ +1200 |
| 6 | 12 | 5 | 3 | 4 | 54.2% | +29 | −182 ~ +268 |
| 8 | 12 | 1 | 1 | 10 | 12.5% | −338 | −1200 ~ −137 |
| 10 | 12 | 1 | 1 | 10 | 12.5% | −338 | −1200 ~ −137 |

→ **交叉点 ≈ Wasabi depth 6.16**。

再把 Wasabi 放到 Stockfish 标尺上 —— 这一步让 **Wasabi 与 Stockfish 直接对打,完全绕开本引擎**,
所以它和 9.5.2 是两条互相独立的证据:

| 对阵 | 局 | Wasabi 得分率 | Wasabi−SF Elo |
|---|---|---|---|
| wasabi d6 vs SF d5 | 12 | 100.0% | > +800 |
| wasabi d6 vs SF d6 | 12 | 75.0% | +191 |
| wasabi d6 vs SF d7 | 12 | 29.2% | −154 |
| wasabi d8 vs SF d6 | 12 | 87.5% | +338 |
| wasabi d8 vs SF d7 | 12 | 66.7% | +120 |
| wasabi d8 vs SF d8 | 12 | 45.8% | −29 |
| wasabi d10 vs SF d8 | 12 | 79.2% | +232 |
| wasabi d12 vs SF d10 | 4 | 50.0% | 0 |
| wasabi d12 vs SF d12 | 4 | 0.0% | < −800 |

→ **Wasabi depth 6 ≈ SF depth 6.55**;**Wasabi depth 8 ≈ SF depth 7.81**;
**Wasabi depth 12 ≈ SF depth 10.00**。
即 **1 个 Wasabi 层 ≈ 0.61~0.63 个 SF 层**(Wasabi 的「层」含更多削减,名义深度更「虚」;
不过这个比值随深度缓增 —— d6 处 0.55、d8 处 0.63)。

#### 9.5.5 两条链路对账 → 默认档 ≈ 2030 Elo

| 链路 | 推导 | 结果 |
|---|---|---|
| ① 本引擎 vs SF 直接测 | 交叉 depth 7.34 | SF d7.34 → **2055 Elo** |
| ② 本引擎 ≈ Wasabi d6.16 → 经 Wasabi↔SF 标定 | 6.55 + 0.16 × 0.63 | SF d6.65 → **2010 Elo** |

**两条独立链路相差仅 0.7 个 SF 层(≈ 45 Elo),取 ≈ 2030 Elo。**

结论:**默认档(高级)大约相当于 2000 ± 60 Elo —— 强俱乐部棋手 / 地方专家水平。**
四档大致是:**初级 ≲1500 / 中级 ≈1990 / 高级 ≈2030 / 大师 ≈2130**。

> 原方案没有写死过四档的目标 Elo(只写了「搜几层」),所以不存在「没达标」的问题。
> chessy 的 README 自称 1500/1700/1900/2100/2300+ 五档(§4.5 已注明那是它自我标定的暂定值,
> 非任何机构认证);按本次实测,chessy 在 160k 节点这一档大致与本引擎同水平。

#### 9.5.6 但单位时间效率上我们是最慢的

同一个局面(意大利变例)下,三个引擎达到「≈2000 Elo」各要花多少:

| 引擎 | 达到该强度所需 | 相对本引擎 |
|---|---|---|
| 本引擎 hard | 160k 节点 / **389ms** | 1× |
| chessy(37KB wasm) | 160k 节点 / **204ms** | ≈1.9× 快 |
| Wasabi(361KB wasm) | ~10~27k 节点 / **25ms** | **≈15× 快** |

> ⚠️ **这 15× 不是「它算得更快」,是「它的节点更值钱」。** 换算成 NPS,两者其实只差约 2 倍
> (由下表反推:Wasabi 在 d12~d14 约 0.84 ~ 0.91M NPS,本引擎约 0.35 ~ 0.42M)。
> 差距几乎全部来自**达到同一棋力所需的节点数差 16.7 倍**。这正是 §3.4 里"评估是弱项"的直接体现:
> 评估准 → 走法排序好 + 前向剪枝的静态判断准 → 同一强度下少搜一个数量级的节点。
> 换句话说,**§9.5.2 里"4 倍节点只买到 63 Elo"和这里的 16.7 倍节点差,是同一个病**:评估不给力时,
> 堆深度换不来棋力。

三者的「深度 × 节点 × 时间」曲线(同一局面):

| 引擎 | 深度 | 节点 | 耗时 |
|---|---|---|---|
| 本引擎 normal | 7 | 40k | 96ms |
| 本引擎 hard | 8 | 160k | 389ms |
| 本引擎 master | 10 | 1.2M | 3424ms |
| chessy | 6 | 160k | 204ms |
| chessy | 7 | 640k | 807ms |
| Wasabi | 6 | 9.6k | 25ms |
| Wasabi | 8 | 26.8k | 28ms |
| Wasabi | 12 | 349k | 414ms |
| Wasabi | 14 | 1.85M | 2033ms |

按 9.5.4 的换算外推,把 Wasabi 放在**与本引擎相同的思考时间**下:

| Wasabi 深度 | 耗时 | 折合 SF depth | ≈ Elo | 该折合值是否直接验证过 |
|---|---|---|---|---|
| 6 | 25ms | 6.55 | 2003 | ✅ 实测交叉点 |
| 8 | 28ms | 7.81 | 2086 | ✅ 实测交叉点 |
| 12 | 414ms(≈本引擎 hard 的耗时) | 10.00 | **2231** | ✅ wasabi d12 vs **SF d10 = 50%**(4 局,正好压线) |
| 14 | 2033ms(≈本引擎 master 的耗时) | 11.56 | **2335** | 外推(未测) |

也就是说:**给 Wasabi 与本引擎默认档相同的思考时间(~0.4s),它搜到 12 层 ≈ +200 Elo;
给到大师档的时间(~2s),约 +300 Elo。** 而我们的曲线已经趋平,它还在往上涨。
(d12 那一行不是纯外推 —— 用 `go depth 12` 的 Wasabi 去打 `go depth 10` 的 Stockfish 正好 50%,
与按 0.63 层/层斜率算出的 SF d10.00 吻合,所以这条外推链是可信的。)

所以 §4.6 不引入 Wasabi 的理由必须说清楚:**那是拿「约一个数量级的单位时间效率」换来的
许可证干净(GPL-3.0 是硬门槛)和体积可控(6.2KB gzip vs 361KB)。**
如果哪天「棋力」的优先级压过「许可证 + 体积」,§五阶段五的 WASM 路线应优先考虑
AssemblyScript 系的现成引擎(§4.1 的补充说明),而不是自己从零写。

### 9.7 搜索侧的耗时剖析:钱花在哪

要谈"搜索还能怎么优化",先得知道时间花在哪。方法(仓库代码未改动,全部在临时目录做插桩副本):

1. 用**插桩副本**数出每个原语每节点被调用多少次(计数不受插桩开销影响);
2. 用**未插桩副本**单独 micro-bench 每个原语的 ns/次;
3. 两者相乘,与实测总耗时对账。

测试局面为开局 / 意大利 / 中局 / 无后中残局四类,节点预算 160k,已做 JIT 预热。

| 原语 | ns/次 | 次/节点 | ns/节点 | 占总时间 |
|---|---|---|---|---|
| **`isLegal`** | 141 | 2.24 | **316** | **13.7%** |
| **`evaluate`** | 655 | 0.68 | **447** | **19.4%** |
| **`genMoves`** | 583 | 0.48 | **279** | **12.1%** |
| **`inCheck`** | 91.5 | 1.00 | **92** | **4.0%** |
| `see` | 131 | 0.42 | 55 | 2.4% |
| 搜索自身的 `make`/`unmake` | 53.5/对 | 0.70 | 37 | 1.6% |
| `isRepetition` | 8.8 | 0.855 | 7.5 | 0.3% |
| `insufficientMaterial` | 13.2 | 0.555 | 7.3 | 0.3% |
| `makeNull`/`unmakeNull` | 21.4/对 | 0.018 | ~0.4 | 0% |
| 小计 | | | 1241 | 53.8% |
| **剩余:递归 / TT / 走法排序 / 循环开销** | | | **1064** | **46.2%** |
| **合计** | | | **2305 ns/节点** | **NPS ≈ 434k** |

> 口径说明:`isLegal` 内部就是 `make` + `attacked()` + `unmake`(易位另走一条路),
> 所以 `make` 的总调用次数是 2.94 次/节点,其中 **2.24 次来自 `isLegal`** ——
> **76% 的 make/unmake 工作只是为了"试一下这个着法合不合法"**,真正被搜索的只占 24%。
> 上表已按"函数"归属、不重复计。

**三条结论:**

1. **瓶颈不是 make/unmake,也不是走法打包**。搜索自身 make/unmake 只占 **1.6%** ——
   §3.2 那套「Int8Array mailbox + int32 打包 + 零对象分配 + 扁平 undo 栈」的设计是有效的,
   这块不用再动。
2. **真正的热点是 `attacked()`**。`isLegal`(13.7%)+ `inCheck`(4.0%)≈ **17.7%**,
   而两者去掉 make/unmake 后几乎全是同一个函数:`attacked()`
   (`inCheck` 就是一句 `attacked(...)`,91.5 ns ≈ 一次 `attacked()`)。
   而它现在是**纯 mailbox 射线扫描** —— 8 个骑士偏移 + 8 个王偏移各循环一遍,
   再加 4 条斜线、4 条直线的 `while` 扫描,每次约 50 次数组访问 + 边界判断 + `rr*8+cc` 乘加。
   **这是全引擎最热的单个函数。**
3. **`evaluate` 占 19.4%**,其中约 41~47% 是兵结构 / 王盾 / 双象那部分(实测:去掉这些后单次成本从 ~600ns 降到 ~350ns)。

**按收益排序的可做项**(Tier 1 是纯速度、不改变任何搜索结果;Tier 2 改的是搜索树):

| | 做什么 | 依据 | 预期 |
|---|---|---|---|
| **T1-1** | **`attacked()` 换成预计算攻击表**:兵/马/王按格查表,滑子用预计算射线 | 单一函数链条吃掉 ~17.7%(`isLegal` 13.7% + `inCheck` 4.0%) | **已实测**:单次 **74.2 → 50.8 ns(1.46×)**,整机 **+5% NPS**(§9.7.1) |
| **T1-2** | **消掉独立的 `isLegal` 一趟**:每节点算一次 `pinned` / `checkers` 掩码,直接生成**合法**着法 | 76% 的 make/unmake 只用于试合法性 | 省掉 ~10% 的节点时间 |
| **T1-3** | **`evaluate` 增量 + 兵结构 hash 表**:子力/PST 在 make/unmake 里增量维护;兵结构/王盾按 Zobrist 兵键缓存 | 占 19.4%,其中 ~45% 是可缓存的兵结构类项 | 合计砍掉 eval 的大半 |
| **T2** | 补搜索技术:见 **§9.8** —— 那里已经把 IIR / countermove / 对数 LMR / LMP / razoring / futility 逐项实测过了 | 我们缺的全是 SF/Wasabi 都有的 | **同深度省 28~66% 节点**,但要逐项过闸门 |

### 9.7.1 T1-1 实测:预计算攻击表值多少

`attacked()` 是纯 mailbox 射线扫描:8 个骑士偏移 + 8 个王偏移各循环一遍,再加 4 条斜线、4 条直线的 `while` 扫描,每次约 50 次数组访问 + 边界判断 + `rr*8+cc` 乘加。把它换成**按格预计算的目标列表**(兵/马/王查表,滑子查预计算射线,命中即 `b[u] === piece(by, X)` 比较)后:

| 指标 | 现状 | 预计算表 | 变化 |
|---|---|---|---|
| `attacked()` 单次成本 | 74.2 ns | 50.8 ns | **1.46×** |
| 每节点调用次数 | 3.21 次 | 3.21 次(完全相同) | — |
| 整机 ns/节点(160k 预算) | 1909.9~2021.1 | 1786.2~1953.1 | **约 +5% NPS** |
| 棋力 | — | — | **0**(见下) |

**验证方式(必须做,否则不敢动)**:① 5 个局面 × 64 格 × 2 方 = 640 组逐格对拍,新旧 `attacked()` 判定完全一致;② 每个局面开一对"全新状态"的引擎各搜一次 160k,深度/节点数/评分/着法**四项逐位相同**;③ 逐格调用计数逐位相同。也就是说这是一个**行为完全不变**的纯加速改动。

> 说明:预计算表省下的是"边界判断 + 地址算术 + 偏移循环",省不掉"从棋盘取数 + 4 条斜线/4 条直线的扫描本身",所以只有 1.46× —— 不是把 17.7% 全变成 0。平均每次省 23.4 ns × 3.21 次/节点 ≈ 75 ns/节点,占 ~1950 ns/节点 的约 4%,与整机实测的 +5% 对得上。

### 9.7.2 先把预期说清楚:Tier 1 换到的不是棋力

这里要纠正本文档上一版的一个错误推论(它把 NPS 直接按"节点→Elo"的斜率换算成了 Elo)。**NPS 在本项目里换不到棋力**,原因是难度档的口径:

- 难度由**节点预算**定义(easy 20k / normal 40k / hard 160k / master 1.2M),`ai.js` 顶部写明这是刻意的 —— 换机器时棋力会漂,但同一台机器上可复现;墙上时间只做兜底。
- 本机 NPS ≈ 43 万 ⇒ hard 的 160k ≈ **0.37s**(兜底 900ms)、master 的 1.2M ≈ **2.8s**(兜底 3500ms)。
- ⇒ **节点预算先到,时间兜底根本不会触发。** 所以 NPS 提升只是让等待变短,一个节点也不会多搜。

结论:**Tier 1(纯速度)在固定难度下 ≈ 0 棋力**;它的真实价值是延迟(把 master 从 2.8s 拉快)和在慢设备/手机上不易撞到时间兜底而变弱。只有当把省下的时间**再换回节点**(调高节点预算)时才会变成棋力 —— 那是一次产品决策。即便按 +5% NPS 同比例调高预算,也只值 log₂(1.05) × 31.5 ≈ **+2 Elo**。

**真正能换棋力的是 Tier 2(剪枝/延伸/排序让"同样节点搜得更深"),也就是 §9.8 逐项实测的那一批。**

**所以搜索侧的排序是明确的:该做,但它换到的是"同预算多 1~2 层",不是翻倍。** 主线仍然是 §9.5 与 `docs/chess-eval-upgrade.md` 里的评估与调参 —— 理由是 §9.5.2 与 §9.6 已经**两条独立证据**证明:本引擎加 4 倍节点只买到 63 Elo,给对手 4 倍节点它也不变强。**评估不给力时,层数本身就不值钱 —— 这一条同样会反过来吃掉 §9.8 的收益。**

最该先做的是 **T1-1**,因为它是纯速度、零棋力风险(逐格 + 逐局面验证过完全一致),顺手把 master 档拉快;而 T1-2 是把引擎从「伪合法 + 逐着试」推向「直接生成合法着法」的唯一机会 —— 那正是我们与 SF/Wasabi 最本质的结构差异之一。

### 9.8 搜索技术移植实测:参考 Wasabi / SF 到底能拿多少

§9.7.2 的结论是"要换棋力只能靠 Tier 2(同深度少花节点)"。这一节把 Tier 2 拆成六个开关逐项实测。

**六项分别是什么**(全是我们没有、而 SF / Wasabi 都有的):

| 代号 | 内容 | SF/Wasabi 对应 |
|---|---|---|
| `iir` | 没有 TT 着法 ⇒ 这层没线索,先降一层 | IIR(internal iterative reduction) |
| `raz` | 静态分离 α 太远 ⇒ 直接进静态搜索取上界 | razoring |
| `fut` | 静着 futility:阈值随 improving 变,适用深度从 ≤2 放宽到 ≤6 | futility pruning |
| `lmp` | 迟着剪枝:阈值随 improving 放大/缩小一倍,并放开原来的"只到深度 3" | LMP(late move pruning) |
| `lmr` | LMR 从台阶式 `r = 1 + (tried > 5+depth*2 ? 1 : 0)` 换成**对数公式** `r = 0.75 + ln(depth)·ln(tried)/2.25`(另有"是否叠加 `!improving → r+1`"的两档) | logarithmic / adaptive LMR |
| `cm` | countermove:记下"对手这步→我最该回敬哪步",排在 killer 之后 | countermove heuristic |

**测法**(全部在临时目录做,仓库代码未改动):

- **局面库**:16 个,覆盖纳伊多夫 / 意大利 / 西班牙 / 后翼弃兵 / 王翼印度 / 法兰西 / 卡罗康 / 英国式 / 斯拉夫 / 尼姆佐 / 格林菲尔德 / 苏格兰 / 彼德罗夫 / 皮尔茨 / 无后中局等;每条走子序列先过 `replayMoves()` 合法性校验。
- **M1 = 固定深度要花多少节点**:`depth: 7` 与 `depth: 8`,各累计 16 个局面的节点总数(越少 = 剪得越有效)。
- **M2 = 固定 160k 节点能搜到第几层**(16 个局面的平均深度)。
- **每个测量点都用全新引擎实例(冷置换表 + 冷 killer/history)。** 这一条是踩坑换来的:第一版复用同一个实例,结果 M1 的深层搜索把结果留在 TT 里,M2 跑到同一局面时白捡一堆 TT 截断,深度虚高好几层,而且**每个变体虚高的幅度还不一样,数字完全不可比**。改成冷实例后 baseline 的 160k 平均深度立刻从 8.19 掉到 7.69。凡是拿"平均深度"做对比的,A/B 必须同口径。
- **正确性闸门用仓库自带的 `test/engine-test.mjs` 全套**(perft / 旧实现对拍 / make-unmake 还原性与 Zobrist 增量 / 规则边角 / 战术 / 残局杀王 / 对旧「一层贪心」胜率,共 **67 项**),用临时副本把 import 指到变体上跑。原版 **67/67 通过**,所以闸门有效、差异可信。

**结果:**

| 改动 | 深度7节点(vs 现状) | 深度8节点(vs 现状) | 160k 平均深度 | 仓库 67 项 |
|---|---|---|---|---|
| 现状 | — (1,028,866) | — (2,316,247) | 7.69 | 全部通过 |
| `iir` | −48.5% | −71.3% | — | **✗ 残局杀王** |
| `cm` | +6.7% | −9.4% | — | **✗ 残局杀王** |
| `lmr`(对数 + improving) | −53.1% | −52.0% | 9.00 | **✗ 后对王杀不掉** |
| `lmr`(对数,去掉 improving 那档) | −31.4% | −43.8% | 8.50 | 全部通过 |
| `lmr`(更保守:系数更小 + 最多减到 depth−3) | **+20.2%** | +2.2% | 7.88 | 全部通过 |
| `lmp` | −27.7% | −18.5% | 8.00 | 全部通过 |
| `lmr`(去 improving) + `lmp` | −37.3% | **−53.7%** | **9.00** | 全部通过 |
| 上一行 + `raz` + `fut` | −38.0% | −54.6% | 9.00 | 全部通过 |
| `lmr`(含 improving) + `lmp`+`raz`+`fut` | −61.9% | −66.2% | 9.75 | 全部通过 |
| 六项全开 | −76.8% | −82.7% | 10.75 | **✗ 残局杀王** |

**四条读数:**

1. **最值钱的一项确实是 LMR**,而且正好就是"参考 SF / Wasabi"能直接拿到的东西。我们的 LMR 是台阶式的 —— 整个搜索里 `r` 只可能是 0 / 1 / 2;换成对数公式后,同深度节点直接砍掉约一半。这是六项里唯一"单项就有量级效果"的。

2. **但不能照抄:`!improving → 再多减一层` 这一档单项就把残局杀王剪没了。** 逐项隔离看得很清楚 —— 只加"对数公式 + improving"时,仓库套件挂在 **「后对王必须在 60 手内将杀」**;把 improving 那一档去掉就恢复 67/67。原因很具体:在"王后对王"这种**静态赢棋**里评估值一直不变 ⇒ `improving` 恒为假 ⇒ 每一着静着都被多减一层;而**将杀恰恰是靠静着(后和王在走)完成的**。我们的引擎只有 9 层深、评估里也没有"把对方的王往死角赶"这类项,**杀棋是靠搜出来的**,一旦把静着剪掉就永远搜不到。SF 敢这么减,是因为它(A)搜得深得多,(B)评估里有把王往死角逼的项,不指望搜索去发现杀棋。**同一条剪枝规则搬到一个小引擎上,剪掉的可能是唯一的取胜路线。**

3. **组合能拿到更多,但要打个问号。** `lmr`(含 improving)+ 其余三项合计省 62~66% 节点、160k 平均深度 7.69 → 9.75(约 +2 层)—— 可是其中 `lmr` 含 improving 的那一版本,单项测时明明挂残局杀王,合起来却过了闸门。这说明这些激进剪枝之间存在**互相掩盖**:过闸门 ≠ 每一项都站得住。所以稳妥的候选是**两个单项各自都过闸门的组合**:`lmr`(去 improving)+ `lmp`,省节点 37%~54%,160k 平均深度 7.69 → 9.00(约 +1.3 层),67 项全过。

4. **自对弈校验:省节点 ≠ 变强。** 拿"现状 vs `lmr`(去 improving)+ `lmp`"下 76 局(38 条合法开局 × 交换先后手,每步固定 15k 节点,成对设计):

   | | 胜 | 和 | 负 | 得分率 | Elo(现状 − 新版) |
   |---|---|---|---|---|---|
   | 现状 vs 新版 | 33 | 22 | 21 | **57.9%** | **+55(95% 区间 −22 ~ +139)** |

   也就是说:**同预算多出来的那 1.3 层,没有转成棋力;点估计反而偏向原版。** 道理和 §9.5.2 / §9.6 是同一个病 —— 剪枝换来的"名义深度"和真正的深度不是一回事:名义上搜到 9 层,但被剪掉的那些分支正是藏着反驳着法的分支,有效精度大概还停在原来的 7~8 层。**这正是 SF 的数字不能移植的原因:SF 的 LMR 收益是在 30+ 层深搜 + 强评估下用自对弈量出来的,我们的 9 层小引擎不满足那个前提。**

**结论:参考 Wasabi / SF 是对的,但"参考"的含义是"知道有哪些技术、然后逐项在自己的闸门和自对弈上证伪",不是抄公式。** 而且实测下来这条路在本引擎上**换不到棋力**(省 54% 节点 = 0,点估计略负),原因与 §9.5.2 / §9.6 的诊断完全一致:**本引擎是评估瓶颈,不是深度瓶颈 —— 评估不给力时,名义层数本身就不值钱。**

所以搜索侧唯一还值得立刻做的仍是 **T1-1**(纯速度、行为逐位不变、模板化无风险);Tier 2 的收益要等 §9.5 与 `docs/chess-eval-upgrade.md` 的评估/调参做完之后,才有必要回来重测 —— 那时候同样的剪枝很可能才开始有正收益。
